# 비밀번호·접속 정보 관리 1단계 설계

- 작성: 2026-10-29
- 상태: 사용자 지시("아 쫌 그냥 추천방법으로 구현까지 진행하라고")에 따라 추천안으로 확정하고 구현한다. 부분별 승인은 받지 않았다.
- tm: 작업 5 (결정 5.2~5.15)
- 디자인: [프론트 표준](../../프론트-표준.md)을 그대로 쓰고, 화면 작업은 `frontend-quality` 스킬 절차를 따른다.

## 1. 목적과 범위

회사 사람 여러 명이 고객사 컴퓨터 원격 접속 정보(아이디·비밀번호·IP)와 DB 접속 정보 같은 민감한 정보를 회사 서버 한 곳에 모아 두고 안전하게 같이 쓴다. 개인 아이디·비밀번호는 본인만 본다. 기존 라이선스 관리도 같은 앱, 같은 로그인 안에서 계속 쓴다.

1단계에 넣는 것:

- 앱 계정(관리자가 초대), 마스터 비밀번호, 2단계 인증, 복구 키
- 종단 간 암호화한 개인 금고와 묶음(공유 폴더)
- 항목 종류 네 가지(원격 접속, DB 접속, 웹사이트 계정, 메모)와 칸별 복사
- 열람 기록, 관리자 화면(사용자·묶음·열람 기록)
- 라이선스 화면을 새 디자인(프론트 표준)으로 옮기고 로그인 뒤에 둔다

1단계에 넣지 않는 것: 브라우저 확장 자동 입력(2단계, tm 5.11), 휴대폰 앱, 묶음 열쇠 교체(전체 재암호화), 항목을 다른 묶음으로 옮기기, 메일 발송, 회사 서버 배포.

완성 기준:

- 권한 있는 직원은 고객사 이름으로 찾아서 몇 번 만에 접속 정보를 복사할 수 있다.
- 묶음에 없는 직원과 DB를 열어 보는 사람은 내용을 못 본다. DB를 통째로 가져가도 못 읽는다.
- 누가 언제 어떤 항목의 비밀번호를 가져갔는지 남는다.
- 마스터 비밀번호를 잊어도 복구 키로 다시 설정할 수 있다.

## 3. 지키는 것과 한계

지키는 것:

- DB를 열어 보거나 통째로 가져간 사람은 묶음 이름, 항목 내용(이름·IP·아이디·비밀번호·메모), 열쇠를 볼 수 없다. 마스터 비밀번호를 알아내려면 사람마다 Argon2id로 느리게 만든 계산을 하나씩 맞혀 봐야 한다.
- 묶음에 없는 직원은 그 묶음의 열쇠 사본이 없어서, 서버가 실수로 암호문을 보내도 풀 수 없다.
- 서버는 비밀 덩어리를 내줄 때마다 열람 기록을 남긴다.

한계(사용자에게도 알린다):

- 서버 프로그램 자체를 몰래 바꿀 수 있는 사람은 브라우저로 내려가는 화면 코드를 바꿔 비밀번호를 가로챌 수 있다. 웹으로 제공하는 종단 간 암호화의 공통 한계다. 서버 프로그램을 고칠 수 있는 사람을 최소로 둔다.
- 서버가 예전 암호문을 다시 내주는 되돌리기는 막지 못한다.
- 이미 본 비밀번호는 되돌릴 수 없다. 구성원을 빼면 "비밀번호 교체 권장" 표시로 실제 비밀번호를 바꾸게 안내한다.
- 마스터 비밀번호와 복구 키를 모두 잃으면 개인 금고는 영구히 못 연다. 묶음은 관리자가 다시 나눠 준다.
- Web Crypto는 보안 컨텍스트에서만 동작한다. 회사 서버는 HTTPS 주소가 필요하다(지금 개발용 localhost는 된다).

## 4. 열쇠 구조와 암호화

모든 암호 연산은 브라우저의 Web Crypto(`crypto.subtle`)로 하고, Argon2id만 `hash-wasm`(MIT)을 쓴다. 바이너리는 JSON에서 base64url(패딩 없음)로 주고받는다.

### 4.1 마스터 비밀번호

1. 가입할 때 브라우저가 사용자별 무작위 소금(16바이트)을 만든다. 소금과 변환 설정(`argon2id`, 메모리 65536KiB, 반복 3, 병렬 4)은 서버에 평문으로 둔다.
2. `master = Argon2id(비밀번호, 소금)` 32바이트.
3. HKDF-SHA256(입력 `master`, 소금 없음)으로 나눈다.
   - `info="km:auth:v1"` → 로그인 확인값 32바이트. 서버로 보낸다.
   - `info="km:master-wrap:v1"` → 마스터 잠금 열쇠(AES-256-GCM). 서버로 보내지 않는다.
4. 서버는 로그인 확인값을 PBKDF2-SHA256(사용자별 무작위 소금 16바이트, 600,000회)으로 다시 해시해 저장하고, 비교는 `timingSafeEqual`로 한다.
5. 마스터 비밀번호는 12자 이상이어야 하고 아이디와 같을 수 없다.

### 4.2 계정 열쇠와 복구 키

- 계정 열쇠: 무작위 AES-256-GCM 열쇠. 개인 항목과 개인키를 잠근다.
- 마스터 잠금 열쇠로 계정 열쇠를 잠근 사본(AAD `km:account-key:master:v1`)을 서버에 둔다.
- 복구 키: 무작위 32바이트를 Crockford base32 52자로 바꿔 4자씩 13묶음으로 한 번 보여 준다. 복구 키에서 HKDF로 나눈다.
  - `info="km:recovery-auth:v1"` → 복구 확인값. 서버는 로그인 확인값과 같은 방식으로 해시해 둔다.
  - `info="km:recovery-wrap:v1"` → 복구 잠금 열쇠. 계정 열쇠를 잠근 두 번째 사본(AAD `km:account-key:recovery:v1`)을 서버에 둔다.
- 복구 키를 한 번 쓰면 새 복구 키를 만들어 다시 보여 준다.

### 4.3 공개키와 개인키

- RSA-OAEP 3072비트, SHA-256. 가입할 때 만든다.
- 공개키(SPKI)는 평문으로, 개인키(PKCS#8)는 계정 열쇠로 잠가(AAD `km:private-key:v1`) 서버에 둔다.

### 4.4 묶음 열쇠

- 묶음마다 무작위 AES-256-GCM 열쇠 하나. 묶음 ID(UUID)는 브라우저가 만든다.
- 구성원과 모든 관리자 각자에게 공개키로 잠근 사본을 준다. RSA-OAEP `label`은 `km:group-key:{묶음ID}:{사용자ID}`로 해서 다른 묶음·사람의 사본과 바꿔치기할 수 없게 한다.
- 묶음 이름은 묶음 열쇠로 잠근다(AAD `km:group-name:{묶음ID}`).

### 4.5 항목

- 항목 ID(UUID)는 브라우저가 만든다. 항목마다 무작위 AES-256-GCM 항목 열쇠를 만든다.
- 항목 열쇠는 묶음 열쇠로 잠근다(AAD `km:item-key:{항목ID}:group:{묶음ID}`). 개인 항목은 계정 열쇠로 잠근다(AAD `km:item-key:{항목ID}:user:{사용자ID}`).
- 내용은 두 덩어리를 각각 항목 열쇠로 잠근다.
  - 요약(AAD `km:item-summary:{항목ID}`): 목록과 검색에 쓰는 칸. 목록을 열 때 한꺼번에 받는다.
  - 비밀(AAD `km:item-secret:{항목ID}`): 비밀번호와 메모. 보기·복사할 때만 따로 받는다.
- AES-GCM은 매번 무작위 12바이트 IV를 쓴다. 암호문 문자열은 `v1.{iv}.{암호문+태그}`, RSA 사본은 `v1r.{암호문}`이다.

### 4.6 서버가 아는 것

- 아는 것: 사용자 이름·아이디·역할·상태, 누가 어느 묶음에 어떤 권한으로 있는지, 항목 ID·소속·개정 번호·시각·작성자, 교체 권장 표시, 열람 기록.
- 모르는 것: 묶음 이름, 항목 종류와 내용 전부, 마스터 비밀번호, 모든 열쇠.

## 5. 사람과 권한

### 5.1 역할과 계정 상태

- 역할: 관리자(`admin`), 직원(`member`). 관리자는 직원이 하는 일에 더해 사용자·묶음·열람 기록을 관리하고 모든 묶음 열쇠를 받는다.
- 상태: 2단계 인증 등록 전(`pending_totp`), 사용 중(`active`), 비활성(`disabled`).
- 처음 설치: 사용자가 한 명도 없으면 서버가 기동할 때 무작위 "처음 설정 코드"(8자)를 서버 콘솔에 찍는다. `/setup` 화면에서 이 코드를 넣어야 첫 관리자를 만들 수 있다. 첫 관리자가 생기면 설정 화면은 닫힌다.
- 관리자는 2명 이상 두라고 관리 화면에서 안내한다. 마지막 관리자는 비활성화하거나 직원으로 바꿀 수 없다.

### 5.2 초대와 가입

1. 관리자가 이름·아이디·역할을 넣어 초대를 만들면 서버가 무작위 토큰(32바이트)을 만들고 해시만 저장한다. 링크(`/invite/{토큰}`)는 72시간 동안 한 번만 쓸 수 있다. 메일은 보내지 않고 관리자가 메신저 등으로 직접 전한다.
2. 초대받은 사람이 링크를 열어 마스터 비밀번호를 정하면, 브라우저가 열쇠(4절)를 모두 만들어 올린다. 복구 키를 보여 주고 "안전한 곳에 보관했어요"를 확인받는다.
3. 이어서 2단계 인증을 등록한다(5.4절). 등록을 마치면 `active`가 된다.
4. 묶음 배정은 관리자가 한다. 새 사람이 공개키를 만든 뒤라야 묶음 열쇠를 건넬 수 있어서, 가입을 마친 사람만 묶음에 넣을 수 있다.
5. 직원으로 초대한 사람은 관리자가 묶음에 넣기 전까지 개인 금고만 쓴다. 관리자로 초대한 사람은 다른 관리자가 "관리자 열쇠 받기"(모든 묶음 열쇠 사본 만들기)를 해 줘야 묶음을 연다.

### 5.3 묶음 권한

- 보기: 묶음의 항목 목록을 보고 비밀번호를 보기·복사한다.
- 수정: 보기 + 항목 추가·수정·삭제.
- 묶음 만들기·이름 바꾸기·삭제, 구성원 추가·제외·권한 바꾸기는 관리자만 한다. 관리자는 자기 브라우저에서 묶음 열쇠를 풀어 새 구성원 몫으로 잠가 올린다.
- 관리자는 구성원이 아니어도 모든 묶음을 수정 권한으로 연다. 화면에는 "관리자 권한으로 보는 중"을 표시하고 열람 기록에 남긴다.

### 5.4 2단계 인증

- TOTP(SHA-1, 6자리, 30초, 앞뒤 1구간 허용)를 `otpauth`(MIT)로 확인한다. 같은 구간의 코드는 두 번 받지 않는다.
- 서버가 비밀값을 만들어 `APP_SECRET_KEY`에서 나눈 열쇠로 암호화해 저장하고, 등록 화면은 브라우저에서 `qrcode`(MIT)로 QR을 그린다.
- 등록을 마치면 예비 코드 10개(각 12자)를 한 번 보여 준다. 서버는 HMAC-SHA256 값만 저장하고, 쓴 코드는 지운다.
- 관리자가 직원의 2단계 인증을 초기화하면 그 사람은 다음 로그인 때 마스터 비밀번호를 넣은 뒤 다시 등록한다. 관리자 본인은 예비 코드를 쓰거나 다른 관리자가 초기화한다. 관리자가 한 명뿐인데 휴대폰과 예비 코드를 모두 잃으면 서버 콘솔 명령(`npm run totp:reset -- <아이디>`)으로 초기화한다.

### 5.5 로그인, 잠금, 재설정

- 로그인: 아이디 → 서버에서 소금과 변환 설정 받기(없는 아이디도 `APP_SECRET_KEY`로 만든 가짜 소금을 돌려줘 존재 여부를 숨김) → 마스터 비밀번호로 로그인 확인값 계산 → 2단계 인증 코드 → 세션 쿠키.
- 로그인 유지 8시간. 그 뒤 처음부터 다시 로그인한다.
- 금고 잠금: 열쇠는 메모리에만 둔다. 15분 동안 조작이 없거나, 잠금 버튼을 누르거나, 새로 고침하면 잠긴다. 다시 열 때는 마스터 비밀번호만 넣는다(브라우저 안에서 계정 열쇠를 풀어 확인).
- 비밀번호 바꾸기: 현재 비밀번호 확인 → 새 소금·설정으로 계정 열쇠를 다시 잠가 올린다.
- 복구: 아이디 + 복구 키 + 2단계 인증 코드 → 계정 열쇠를 복구 사본에서 꺼내 새 마스터 비밀번호로 잠그고, 새 복구 키를 만든다.
- 시도 제한: 같은 계정에서 로그인·복구·2단계 인증이 5번 연속 틀리면 15분 잠근다. IP마다 인증 요청은 1분에 20번까지 받는다.

### 5.6 퇴사·권한 회수

- 관리자가 사용자를 비활성화하면 세션을 모두 끊고, 그 사람의 묶음 열쇠 사본을 모두 지우고, 그 사람이 열 수 있던 묶음의 항목에 "비밀번호 교체 권장"을 표시한다.
- 구성원에서 뺄 때도 같은 표시를 한다.
- 항목을 고칠 때 "비밀번호를 새로 바꿨어요"를 고르면 표시를 지운다.

## 6. 항목 종류와 칸

| 종류 | 요약(목록·검색용) | 비밀 |
|---|---|---|
| 원격 접속 `remote` | 이름*, 업체, 접속 방식(RDP·AnyDesk·TeamViewer·SSH·VNC·기타), 주소(IP·호스트·원격 ID), 포트, 아이디 | 비밀번호, 메모 |
| DB 접속 `database` | 이름*, 업체, DB 종류(SQL Server·PostgreSQL·MySQL/MariaDB·Oracle·기타), 주소, 포트, DB 이름, 아이디 | 비밀번호, 메모 |
| 웹사이트 계정 `website` | 이름*, 업체, 주소(URL), 아이디 | 비밀번호, 메모 |
| 메모 `note` | 이름*, 업체 | 내용 |

- `*`는 필수. 각 글자 칸은 500자, 메모는 10,000자까지.
- 검색은 브라우저에서 푼 요약(이름·업체·주소·아이디·DB 이름)을 대상으로 한다.
- 칸마다 복사 버튼을 둔다. 비밀번호 복사·보기는 서버에서 비밀 덩어리를 받아 온다. 복사한 값은 30초 뒤 클립보드가 그 값 그대로면 지운다(읽기 권한이 없으면 그냥 지운다).
- 항목 만들기·고치기 화면에 비밀번호 만들기 버튼(20자, 영문 대소문자·숫자·기호)을 둔다.

## 7. 화면

프론트 표준의 토큰·coss ui 컴포넌트·화면 패턴을 쓴다. 왼쪽(넓은 화면) 또는 위쪽(좁은 화면) 메뉴로 금고·라이선스·관리를 오간다.

| 주소 | 화면 | 누가 |
|---|---|---|
| `/setup` | 처음 설정: 설정 코드 → 관리자 정보·마스터 비밀번호 → 복구 키 → 2단계 인증 → 예비 코드 | 처음 한 번 |
| `/login` | 아이디 → 마스터 비밀번호 → 인증 코드(예비 코드 쓰기 링크) | 모두 |
| `/invite/:token` | 초대 수락: 마스터 비밀번호 → 복구 키 → 2단계 인증 → 예비 코드 | 초대받은 사람 |
| `/recover` | 아이디·복구 키·인증 코드 → 새 마스터 비밀번호 → 새 복구 키 | 모두 |
| (잠금) | 금고 열기: 마스터 비밀번호 | 로그인한 사람 |
| `/vault` | 금고: 개인 금고·묶음 목록, 검색, 종류 필터, 항목 표, 상세 패널(칸별 복사, 비밀번호 보기), 항목 만들기·고치기·삭제 | 모두 |
| `/licenses` | 라이선스(새 디자인) | 모두 |

| `/admin/groups` | 묶음: 만들기, 이름 바꾸기, 구성원·권한, 삭제 | 관리자 |

- 비밀번호·복구 키·예비 코드는 화면에 기본으로 가리고, 보기 버튼으로 잠깐 보인다.
- 각 화면은 불러오는 중·빈 목록·오류·권한 없음 상태를 따로 보여 준다.

## 8. API

모든 요청은 같은 출처의 `/api`로 보낸다(개발 서버는 Vite proxy가 백엔드 5000으로 넘긴다). 로그인이 필요한 요청은 세션 쿠키와 `X-KM-Request: 1` 머리글이 있어야 한다.

| 묶음 | 요청 | 설명 |
|---|---|---|
| 상태 | `GET /auth/status` | `{ setupRequired }` |
| 설정 | `POST /auth/setup` | 설정 코드 + 첫 관리자 열쇠 자료 → 등록용 세션 |
| 로그인 | `POST /auth/prelogin` | `{ loginId }` → 소금·변환 설정 |
| | `POST /auth/login` | `{ loginId, authValue }` → `totp_required` 또는 `totp_enroll_required` |
| | `POST /auth/login/totp` | `{ code }` 또는 `{ backupCode }` → 세션, 내 정보·잠긴 열쇠 |
| | `POST /auth/logout`, `GET /auth/me` | |
| 2단계 인증 | `POST /auth/totp/enroll/start`, `POST /auth/totp/enroll/confirm` | QR용 주소 / 코드 확인 → 예비 코드 |
| 계정 | `POST /auth/password` | 현재 확인값 + 새 소금·설정·확인값·계정 열쇠 사본 |
| 복구 | `POST /auth/recover/start`, `POST /auth/recover/complete` | 복구 확인값 + 코드 → 복구 사본 / 새 비밀번호·새 복구 키 |
| 초대 | `GET/POST /invites`, `DELETE /invites/:id` | 관리자 |
| | `GET /invites/:token`, `POST /invites/:token/accept` | 초대받은 사람(로그인 없음) |
| 사용자 | `GET /users` | 관리자: 목록·공개키 |
| | `PATCH /users/:id/role` | 관리자로 올릴 때 모든 묶음 열쇠 사본을 함께 보낸다 |
| | `POST /users/:id/disable`, `POST /users/:id/enable`, `POST /users/:id/totp-reset` | 관리자 |

## 9. DB 표

새 마이그레이션 하나로 아래 표를 만든다. 기존 `license_keys`는 고치지 않는다.

- `users`: `id uuid PK`, `login_id varchar(64) UNIQUE`(소문자로 저장), `name varchar(100)`, `role`, `status`, `kdf_salt`, `kdf_params jsonb`, `auth_hash`, `auth_salt`, `recovery_auth_hash`, `recovery_auth_salt`, `account_key_master text`, `account_key_recovery text`, `public_key text`, `private_key_enc text`, `totp_secret_enc text NULL`, `totp_last_step bigint NULL`, `backup_codes jsonb`, `failed_attempts int`, `locked_until timestamptz NULL`, `last_login_at`, `created_at`, `updated_at`
- `invites`: `id uuid PK`, `token_hash UNIQUE`, `login_id`, `name`, `role`, `created_by FK users`, `expires_at`, `used_at NULL`, `revoked_at NULL`, `created_at`
- `sessions`: `id uuid PK`, `token_hash UNIQUE`, `user_id FK users`, `stage`(`full`·`pending_totp`·`enroll_totp`·`recovery`), `expires_at`, `revoked_at NULL`, `ip`, `user_agent`, `created_at`
- `vault_groups`: `id uuid PK`, `name_enc text`, `created_by FK users`, `created_at`, `updated_at`
- `vault_group_access`: `(group_id, user_id) PK`, `permission`(`view`·`edit`), `is_member bool`, `wrapped_key text`, `created_at`, `updated_at`. 묶음 삭제 시 함께 지운다.
- `vault_items`: `id uuid PK`, `group_id uuid NULL FK`, `owner_user_id uuid NULL FK`, 둘 중 하나만 있다는 CHECK, `item_key_enc text`, `summary_enc text`, `secret_enc text`, `revision int`, `needs_rotation bool`, `created_by`, `updated_by`, `created_at`, `updated_at`
- `audit_events`: `id bigserial PK`, `at timestamptz`, `actor_user_id uuid NULL`, `action varchar(40)`, `target_type`, `target_id`, `group_id NULL`, `detail jsonb`(비밀 없음), `ip`, `user_agent`

암호문 칸은 길이 상한을 둔다(요약 16KiB, 비밀 32KiB, 열쇠 사본 2KiB).

## 10. 열람 기록

서버가 남기는 사건: 로그인 성공·실패·계정 잠김, 2단계 인증 등록·초기화·예비 코드 사용, 비밀번호 바꾸기, 복구 사용, 초대 만들기·취소·수락, 역할 바꾸기, 비활성화·다시 활성화, 묶음 만들기·이름 바꾸기·삭제, 구성원 추가·제외·권한 바꾸기, 항목 만들기·고치기·삭제, 비밀 보기·복사(`secret_view`·`secret_copy`). 관리자가 구성원이 아닌 묶음을 열면 `detail.asAdmin=true`를 붙인다.

열람 기록 화면은 관리자가 가진 묶음 열쇠로 항목·묶음 이름을 풀어 보여 준다. 개인 항목은 "개인 항목"으로만 보인다.

## 11. 서버 보안 설정

- `APP_SECRET_KEY`(base64 32바이트) 하나를 `.env`에 두고, HKDF로 2단계 인증 비밀값 암호화·예비 코드 HMAC·가짜 소금·세션 토큰 해시용 열쇠를 나눈다. `npm run secrets:init`이 값이 없을 때만 무작위로 만들어 `.env`에 넣고 화면에 찍지 않는다.
- 세션 쿠키 `km_session`: httpOnly, SameSite=Strict, Secure(개발 localhost에서도 켬, `COOKIE_SECURE=false`로만 끔), 경로 `/`. DB에는 토큰의 HMAC만 둔다.
- CSRF: SameSite=Strict + 로그인 필요한 모든 요청에 `X-KM-Request: 1` 머리글 확인. CORS는 지금처럼 허용 출처만, 자격 증명은 허용하지 않는다.
- 요청 제한: `@nestjs/throttler`로 인증 요청을 IP마다 1분 20번.
- 화면 CSP: 빌드한 `index.html`에 `<meta http-equiv="Content-Security-Policy">`를 넣는다. `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'`. 개발 서버(HMR)에는 넣지 않는다.
- 서버 로그와 오류 응답에 확인값·토큰·암호문을 남기지 않는다.

## 12. 오류 처리

- 풀기 실패(위조·열쇠 불일치): 그 항목만 "이 항목을 열 수 없어요"로 표시하고 나머지는 계속 보여 준다.
- 세션 만료(401): 열쇠를 지우고 로그인 화면으로 보낸다.
- 권한 없음(403): 금고를 다시 불러온다. 구성원에서 빠진 경우 그 묶음이 목록에서 사라진다.
- 동시 수정(409): "다른 사람이 먼저 고쳤어요. 새 내용을 불러온 뒤 다시 고치세요."
- 네트워크 오류: 입력한 내용은 지우지 않고 다시 시도 버튼을 보인다.
- 모든 오류 문구는 한국어로, 무엇을 하면 되는지 함께 쓴다.

## 13. 시험과 검증

- 프론트 암호 모듈(Vitest, Node 환경): Argon2id 알려진 답(RFC 9106), 묶음·항목 암호화 왕복, 한 바이트 위조·다른 AAD·다른 열쇠에서 실패, 복구 키 형식 왕복, 계정 만들기 → 잠금 해제 → 비밀번호 바꾸기 → 복구 흐름.
- 백엔드 단위 시험: 확인값 해시·비교, TOTP 확인·재사용 거부, 예비 코드, 가짜 소금, 권한 판정.
- 백엔드 e2e(시험 DB `keymanager_test`): 설정 → 초대 → 가입 → 2단계 인증 → 로그인 → 묶음 → 구성원 → 항목 → 비밀 열람 기록, 비구성원 403, 보기 권한의 수정 403, 비활성화 뒤 세션·열쇠 사본 삭제, 시도 제한, CSRF 머리글 없는 요청 거부, 라이선스 API 로그인 필요.
- 브라우저(Playwright): 관리자·직원 두 사람으로 전체 흐름, 잠금·잠금 해제, 복사 후 클립보드, 빌드본(`vite preview`)에서 CSP 아래 동작, `frontend-quality` 검증 기준(키보드, 대비, 1440·768·390 폭, 다크, 낮은 창, 움직임 줄이기, 한국어).
- DB 확인: 시험 자료의 비밀번호·이름·IP 글자가 DB 어느 칸에도 평문으로 없는지 읽기 전용 조회로 확인한다.
- 짝(Codex) 교차 검토: 암호 모듈, 인증·권한 API, 화면을 단계마다 따로 본다.

## 14. 구현 순서

각 단계는 시험을 먼저 쓰고(TDD), 검사(타입·린트·시험·빌드·취약점)를 종료 코드로 확인한 뒤 커밋한다.

1. 백엔드 기반: `APP_SECRET_KEY`와 `secrets:init`, 쿠키, 세션·CSRF 가드, 요청 제한, 열람 기록 서비스.
2. 백엔드 계정: 설정·로그인·2단계 인증·로그아웃·내 정보·비밀번호 바꾸기·복구·초대. 마이그레이션을 시험 DB에 적용하기 전에 사용자 승인을 받는다.
3. 백엔드 금고: 묶음·구성원·항목·비밀 열람, 사용자 관리, 열람 기록 조회, 라이선스 API에 로그인 가드.
4. 프론트 암호 모듈(`src/lib/crypto`).
5. 프론트 기반: `/api` proxy, API 클라이언트, 라우터, 세션·금고 상태(자동 잠금), 앱 틀(메뉴), 빌드 CSP.
6. 인증 화면: 처음 설정, 로그인, 초대 수락, 복구, 금고 열기, 내 계정.
7. 금고 화면과 관리자 화면.
8. 라이선스 화면을 새 디자인으로 옮기고 `components/legacy`와 Radix·sonner 의존성을 지운다.
9. 전체 검증과 짝 교차 검토, tm 갱신, 완료 보고.

## 1. 목적과 범위

회사 사람 여러 명이 고객사 컴퓨터 원격 접속 정보(아이디·비밀번호·IP)와 DB 접속 정보 같은 민감한 정보를 회사 서버 한 곳에 모아 두고 안전하게 같이 쓴다. 개인 아이디·비밀번호는 본인만 본다. 기존 라이선스 관리도 같은 앱, 같은 로그인 안에서 계속 쓴다.

1단계에 넣는 것:

- 앱 계정(관리자가 초대), 마스터 비밀번호, 2단계 인증, 복구 키
- 종단 간 암호화한 개인 금고와 묶음(공유 폴더), 공개키 확인, 구성원을 뺄 때 묶음 열쇠 교체
- 항목 종류 네 가지(원격 접속, DB 접속, 웹사이트 계정, 메모)와 칸별 복사
- 열람 기록, 관리자 화면(사용자·묶음·열람 기록)
- 라이선스 화면을 새 디자인(프론트 표준)으로 옮기고 로그인 뒤에 둔다

1단계에 넣지 않는 것: 브라우저 확장 자동 입력(2단계, tm 5.11), 휴대폰 앱, 항목을 다른 묶음으로 옮기기, 메일 발송, 회사 서버 배포, 서버 콘솔로 관리자를 지정하는 비상 명령.

완성 기준:

- 권한 있는 직원은 고객사 이름으로 찾아서 몇 번 만에 접속 정보를 복사할 수 있다.
- 묶음에 없는 직원과 DB를 열어 보는 사람은 내용을 바로 읽을 수 없다(3절의 조건과 한계 안에서).
- 누가 언제 어떤 항목의 비밀을 서버에서 받아 갔는지 남는다.
- 마스터 비밀번호를 잊어도 복구 키로 다시 설정할 수 있다.

## 3. 지키는 것과 한계

"앱 관리자"는 KeyManager 안에서 사용자·묶음을 관리하는 역할이다. 서버 컴퓨터나 DB를 운영하는 사람(서버·DB 운영자)과 다르다. 앱 관리자는 결정 5.12에 따라 모든 묶음을 열 수 있다.

| 공격자 | 지키는 것 | 못 지키는 것 |
|---|---|---|
| DB를 읽기만 하거나 통째로 가져간 사람 | 암호문만으로는 묶음 이름·항목 내용·열쇠를 바로 읽을 수 없다. 마스터 비밀번호는 사람마다 Argon2id(64MiB)로 하나씩 추측해야 한다. | 마스터 비밀번호가 약하면 오프라인 추측으로 뚫릴 수 있다. 그래서 강도 조건(4.1절)을 건다. 항목 수·암호문 길이·묶음 구성·시각·IP로 조직과 행동은 어느 정도 추론된다. |
| DB를 고칠 수 있는 사람 | 공개키를 바꿔치기해도 관리자가 확인한 열쇠가 아니면 묶음 열쇠를 건네지 않는다. 관리자·구성원 명단에 사람을 끼워 넣어도, 관리자 브라우저는 확인된 관리자가 서명한 명단(관리자 승인 서명, 묶음 열쇠 사본 서명)에 있는 사람에게만 새 열쇠를 건넨다(4.5절, 짝 재확인 1). 초대의 대상·역할·만료를 바꾸면 초대 링크 확인이 실패한다. 가짜 묶음 열쇠를 넣어도 확인한 관리자의 서명이 없으면 쓰지 않는다. 암호문을 다른 항목·칸·개정으로 옮기면 풀리지 않는다. | 예전 암호문으로 되돌리는 것, 해임 전의 관리자 승인처럼 예전에 유효했던 서명 자료를 되살리는 것, 열람 기록을 지우거나 꾸미는 것은 막지 못한다. 직원이 안전 번호로 직접 확인한 다른 사람이 DB 변조와 짜고 가짜 묶음 열쇠를 건네는 경우도 막지 못한다. |
| 서버 프로그램이나 배포를 장악한 사람 | 없음 | 브라우저로 내려가는 화면 코드를 바꿔 비밀번호를 가로챌 수 있다. 웹으로 제공하는 종단 간 암호화의 공통 한계다. 서버 프로그램을 고칠 수 있는 사람을 최소로 둔다. |
| 묶음에 없는 직원 | 그 묶음의 열쇠 사본이 없어서 서버가 실수로 암호문을 보내도 풀 수 없다. 서버도 매 요청마다 권한을 따로 검사한다. | 없음 |
| 구성원에서 빠진 사람 | 묶음 열쇠를 새 세대로 바꾸므로, 뺀 뒤에 새로 만들거나 고친 항목은 풀 수 없다. | 이미 본 비밀번호와, 빠지기 전에 받아 둔 열쇠·암호문으로 풀 수 있는 그 시점의 내용은 되돌릴 수 없다. 그래서 그 사람이 볼 수 있던 항목에 "비밀번호 교체 권장"을 표시하고, 실제 비밀번호를 바꾼 뒤 저장하게 한다. |

그 밖의 한계: 마스터 비밀번호와 복구 키를 모두 잃으면 개인 금고는 영구히 못 연다. 관리자가 모두 열쇠를 잃으면 관리자만 가진 묶음은 복구할 수 없다(5.1절에서 관리자 2명 이상을 안내). 마지막 관리자가 마스터 비밀번호와 복구 키를 모두 잃으면 1단계에서는 앱 관리 기능(초대·묶음·권한)을 되살리는 방법이 없다(5.6절, 짝 재확인 2). Web Crypto는 보안 컨텍스트에서만 동작하므로 회사 서버는 HTTPS 주소가 필요하다. 브라우저 메모리를 물리적으로 지운다고 보장하지 않는다.

## 4. 열쇠 구조와 암호화

암호 연산은 브라우저의 Web Crypto(`crypto.subtle`)로 하고 Argon2id만 `hash-wasm`(MIT, 버전 고정)을 쓴다. 바이너리는 base64url(패딩 없음, 아래 b64u)로 주고받고, 글자는 UTF-8로 바꾼다. 형식 버전은 모두 `v1`이다.

### 4.1 마스터 비밀번호

- 비밀번호는 `normalize("NFC")` 뒤 UTF-8로 바꾼다.
- 강도 조건: 12자 이상, `@zxcvbn-ts/core`+`@zxcvbn-ts/language-common`(MIT, 브라우저 안에서만 검사) 점수 3 이상, 아이디·이름을 포함하지 않음, 바꿀 때 지금 비밀번호와 다름. 외부 서비스로 비밀번호나 해시를 보내지 않는다.
- 변환: Argon2id v1.3, 소금 16바이트(가입할 때 브라우저가 만들고 서버에 평문 저장), memorySize 65536KiB(64MiB), iterations 3, parallelism 4, 출력 32바이트 binary. 웹 작업자(Web Worker)에서 돌린다.
- 브라우저는 서버가 준 설정이 memorySize 65536~262144KiB, iterations 3~10, parallelism 1~4를 벗어나면 계산하지 않는다(너무 약하거나 너무 무거운 설정 거부).
- HKDF-SHA256(입력 `master`, 소금 0바이트)으로 32바이트씩 나눈다.
  - `info="km:v1:auth"` → 로그인 확인값. 서버로 보낸다.
  - `info="km:v1:master-wrap"` → 마스터 잠금 열쇠(AES-256-GCM, 내보내기 불가).
- 서버는 로그인 확인값을 PBKDF2-SHA256(사용자별 무작위 소금 16바이트, 600,000회)으로 다시 해시해 저장하고 `timingSafeEqual`로 비교한다.

### 4.2 계정 열쇠와 복구 키

- 사용자 ID(UUID)는 가입하는 브라우저가 만든다.
- 계정 열쇠: 무작위 AES-256-GCM 열쇠. 개인 항목, 개인키, 확인 기록, 초대 비밀을 잠근다.
- 마스터 잠금 열쇠로 잠근 사본: AAD `km:v1:account-key:master:{userId}`.
- 복구 키: 무작위 30바이트 + SHA-256 앞 2바이트 검사값 = 32바이트를 Crockford base32 52자로 바꿔 4자씩 13묶음으로 보여 준다. 입력할 때 검사값으로 오타를 먼저 잡는다. HKDF(입력 30바이트)로 나눈다.
  - `info="km:v1:recovery-auth"` → 복구 확인값. 서버는 로그인 확인값과 같은 방식으로 해시해 둔다.
  - `info="km:v1:recovery-wrap"` → 복구 잠금 열쇠. 계정 열쇠를 잠근 두 번째 사본(AAD `km:v1:account-key:recovery:{userId}`)을 둔다.
- 복구 키를 한 번 쓰면 새 복구 키를 만들어 다시 보여 준다.

### 4.3 공개키와 서명 열쇠

- 암호화용: RSA-OAEP 3072비트, SHA-256. 공개키(SPKI)는 평문, 개인키(PKCS#8)는 계정 열쇠로 잠근다(AAD `km:v1:private-key:enc:{userId}`).
- 서명용: ECDSA P-256, SHA-256. 공개키(SPKI)는 평문, 개인키는 계정 열쇠로 잠근다(AAD `km:v1:private-key:sign:{userId}`).
- 풀어 쓸 때는 내보내기 불가 열쇠로 들여온다.
- 안전 번호: 4.9절 형식으로 `safety-number` 입력(두 사람의 사용자 ID·암호화 공개키·서명 공개키를 사용자 ID 오름차순으로)을 만들어 SHA-256을 구한다. 앞 30바이트를 5바이트씩 6조각으로 나눠, 각 조각을 부호 없는 40비트 큰 끝(big-endian) 정수로 읽고 100000으로 나눈 나머지를 앞을 0으로 채운 5자리로 쓴다(5자리 숫자 6묶음). 두 사람이 각자 화면에서 계산하므로 서버가 준 문자열을 비교하는 것이 아니다.

### 4.4 공개키 확인(짝 검토 2)

- 확인 기록: "내가 이 사람의 이 공개키들을 확인했다"는 기록을 내 계정 열쇠로 잠가(AAD `km:v1:trust:{내ID}:{상대ID}`) 서버에 둔다. DB를 고칠 수 있는 사람도 내 계정 열쇠 없이는 만들거나 고칠 수 없다.
- 초대 링크로 자동 확인: 관리자가 초대를 만들 때 브라우저가 토큰 T(32바이트)와 비밀 S(32바이트)를 만든다. 링크는 `/invite#{b64u(T)}.{b64u(S)}`로, 둘 다 주소의 `#` 뒤에 있어서 서버 요청·로그·Referer에 남지 않는다. 관리자는 S를 자기 계정 열쇠로 잠가(AAD `km:v1:invite-secret:{초대ID}`) 서버에 두고, 초대 MAC `HMAC-SHA256(S, invite-offer 입력)`도 함께 둔다. invite-offer 입력(4.9절)은 초대 ID, 초대한 관리자 ID, 대상 아이디, 이름, 초대 역할, 만료 시각, 관리자 암호화 공개키, 관리자 서명 공개키다(짝 재확인 1).
  - 초대받은 사람은 링크의 S로 초대 MAC을 다시 계산해 관리자 공개키와 초대 내용(아이디·이름·역할·만료)을 확인하고, 그 관리자에 대한 확인 기록을 만든다. 수락 MAC `HMAC-SHA256(S, invite-accept 입력)`을 올린다. invite-accept 입력은 초대 ID, 새 사용자 ID, 아이디, 초대 역할, 암호화 공개키, 서명 공개키다.
  - 초대한 관리자의 브라우저는 금고를 열 때 S를 풀어 두 MAC을 서버가 준 초대 행으로 다시 계산해 확인한다. 맞으면 그 사람에 대한 관리자 쪽 확인 기록을 만들고 `POST /invites/:id/verify`로 확인 완료를 알린다(서버는 이때만 `verified_at`을 채운다). 초대 역할이 관리자면 같은 요청에서 관리자로 올린다(5.1절). 맞지 않으면 "초대 수락 정보가 바뀌었을 수 있어요"로 막는다.
  - 초대받은 사람이 관리자를 확인한 기록과, 관리자가 초대받은 사람을 확인한 기록은 서로 다른 기록이다. 서버는 기록 내용을 풀 수 없으므로 `verified_at`은 공유 권한 판단에 쓰지 않고 화면 표시용으로만 쓴다.
- 안전 번호로 수동 확인: 초대한 관리자가 아닌 관리자와 직원 사이는 두 사람이 전화나 대면으로 안전 번호를 비교하고 "확인했어요"를 누른다.
- 확인한 공개키가 서버에서 바뀌어 있으면 자동으로 다시 믿지 않고 경고한 뒤 다시 확인하게 한다.

### 4.5 묶음 열쇠와 세대

- 묶음마다 무작위 AES-256-GCM 열쇠가 있고 세대 번호(1부터)가 붙는다. 묶음 ID(UUID)는 브라우저가 만든다.
- 관리자는 확인 기록이 있는 사람에게만 묶음 열쇠를 건넨다. RSA-OAEP로 잠그고 `label`은 `km:v1:group-key:{묶음ID}:g{세대}:{받는ID}`다.
- 관리자 승인 서명: 관리자로 올릴 때 올리는 관리자가 admin-grant 입력(4.9절: 대상 ID, 아이디, 암호화 공개키, 서명 공개키)에 서명한다. 첫 관리자는 처음 설정 때 자기 서명을 둔다. 관리자 브라우저는 자기 자신에서 시작해, 자기 승인을 서명한 관리자와 이미 믿은 관리자가 서명한 승인만 따라가 "확인된 관리자" 목록을 만든다. 서버가 관리자라고 해도 이 목록에 없으면 관리자로 믿지 않고 경고한다(짝 재확인 1).
- 건네는 관리자는 group-key-share 입력(4.9절: 묶음 ID, 세대, 받는 ID, 건넨 ID, 권한, 구성원 여부, 잠긴 사본)에 서명한다. 받는 사람은 건넨 관리자의 확인 기록이 있고 서명이 맞을 때만 그 열쇠를 쓴다. 없으면 "이 묶음 열쇠를 건넨 관리자를 아직 확인하지 않았어요"로 안전 번호 확인을 안내한다.
- 새 세대 열쇠를 받을 사람(묶음 만들기·열쇠 교체)은 관리자 브라우저가 서버 명단을 그대로 믿지 않고 정한다. "지금 세대 사본의 서명이 확인된 관리자의 서명으로 맞는 사람"에서 빼는 사람을 빼고, "확인된 관리자" 전원을 더한다. 서명이 맞지 않는 행이 있으면 그 사람을 넣지 않고 관리자에게 알린다. 서버도 남은 사람 목록이 정확히 맞아야만 받으므로, 그런 행이 있으면 교체가 끝나지 않은 것으로 남는다.
- 묶음 이름은 그 세대의 묶음 열쇠로 잠근다(AAD `km:v1:group-name:{묶음ID}:g{세대}`).
- 구성원을 빼거나, 사용자를 비활성화하거나, 관리자를 직원으로 바꿀 때는 같은 요청 안에서 그 사람이 열 수 있던 묶음마다 새 세대 열쇠를 만들어, 남은 구성원과 모든 관리자에게 다시 건네고, 묶음 이름과 그 묶음의 모든 항목 열쇠를 새 세대 열쇠로 다시 잠근다(짝 검토 3). 서버는 세대·남은 사람 목록·항목 목록이 빠짐없이 맞을 때만 한 번에 바꾼다.

### 4.6 항목

- 항목 ID(UUID)는 브라우저가 만든다. 항목 열쇠는 무작위 AES-256-GCM이고, **항목을 만들거나 고칠 때마다 새로 만든다**(옛 항목 열쇠로 새 내용을 풀 수 없게).
- 항목 열쇠는 묶음 열쇠로 잠근다(AAD `km:v1:item-key:{항목ID}:group:{묶음ID}:g{세대}`). 개인 항목은 계정 열쇠로 잠근다(AAD `km:v1:item-key:{항목ID}:user:{사용자ID}`).
- 내용은 두 덩어리를 각각 항목 열쇠로 잠근다. 개정 번호를 AAD에 넣어 다른 개정의 덩어리와 섞이지 않게 한다.
  - 요약(AAD `km:v1:item-summary:{항목ID}:r{개정}`): 목록과 검색에 쓰는 칸.
  - 비밀(AAD `km:v1:item-secret:{항목ID}:r{개정}`): 비밀번호와 메모. 보기·복사할 때만 따로 받는다.

### 4.7 암호문 형식

- AES-GCM: 매번 새 무작위 12바이트 IV, 128비트 태그. `v1.{b64u(iv)}.{b64u(암호문+태그)}`. IV는 어떤 두 암호문도 공유하지 않는다.
- RSA-OAEP: `v1r.{b64u}`. ECDSA 서명: `v1s.{b64u}`(IEEE P1363 형식).
- AAD·label이 다르거나, 형식 버전이 다르거나, 태그가 틀리면 풀기를 거부한다.

### 4.8 서버가 아는 것

- 아는 것: 사용자 이름·아이디·역할·상태, 공개키들, 누가 어느 묶음에 어떤 권한으로 있는지, 묶음 세대, 항목 ID·소속·개정 번호·세대·시각·작성자, 교체 권장 표시, 열람 기록.
- 모르는 것: 묶음 이름, 항목 종류와 내용 전부, 마스터 비밀번호, 복구 키, 초대 비밀, 모든 비밀 열쇠.

### 4.9 서명·MAC·안전 번호 입력 형식(짝 재확인 권장 1)

- 입력은 UTF-8 글자열이다. 첫 줄은 `km:v1:{목적}`이고, 그 아래에 정해진 순서의 값을 한 줄에 하나씩 두어 줄 바꿈(LF 한 글자)으로 잇는다. 마지막 줄 뒤에는 줄 바꿈을 두지 않는다.
- 값은 줄 바꿈이 들어갈 수 없는 형식만 쓴다. 소문자 UUID, b64u, 소문자 아이디, 역할·권한 낱말(`admin`·`member`·`view`·`edit`), 참거짓(`true`·`false`), 10진 정수, `toISOString()` 형식의 UTC 시각이다. 이름처럼 아무 글자나 들어갈 수 있는 값은 UTF-8을 b64u로 바꿔 넣는다.

| 목적 | 값(순서대로) |
|---|---|
| `invite-offer` | 초대 ID, 관리자 ID, 대상 아이디, 이름(b64u), 역할, 만료 시각, 관리자 암호화 공개키, 관리자 서명 공개키 |
| `invite-accept` | 초대 ID, 새 사용자 ID, 아이디, 역할, 암호화 공개키, 서명 공개키 |
| `admin-grant` | 대상 ID, 아이디, 암호화 공개키, 서명 공개키 |
| `group-key-share` | 묶음 ID, 세대, 받는 ID, 건넨 ID, 권한, 구성원 여부, 잠긴 사본 |
| `safety-number` | 앞사람 ID, 앞사람 암호화 공개키, 앞사람 서명 공개키, 뒷사람 ID, 뒷사람 암호화 공개키, 뒷사람 서명 공개키(사용자 ID 오름차순) |

- 프론트 암호 모듈에 목적마다 알려진 답(고정 입력 → 고정 바이트·결과)을 시험으로 남긴다.

## 5. 사람과 권한

### 5.1 역할과 계정 상태

- 역할: 관리자(`admin`), 직원(`member`). 관리자는 직원이 하는 일에 더해 사용자·묶음·열람 기록을 관리하고 모든 묶음 열쇠를 받는다.
- 상태: 2단계 인증 등록 전(`pending_totp`), 사용 중(`active`), 비활성(`disabled`).
- 공개 가입은 없다. 처음 설치 때만 첫 관리자를 만들고, 그 뒤로는 초대로만 계정이 생긴다.
- 처음 설치: 사용자가 없으면 서버가 기동할 때 무작위 "처음 설정 코드"(Crockford base32 10자)를 서버 콘솔에만 찍는다. `/setup`에서 이 코드를 넣어야 첫 관리자를 만들 수 있고, 만들기는 "사용자가 0명"을 확인하는 한 번의 트랜잭션으로 한다. 첫 관리자가 생기면 설정 경로는 닫힌다.
- 관리자가 한 명뿐이면 관리 화면 위쪽에 "관리자가 한 명뿐이에요. 열쇠를 잃으면 묶음을 복구할 수 없으니 관리자를 한 명 더 지정하세요"를 계속 보인다. 마지막 관리자는 비활성화하거나 직원으로 바꿀 수 없다.
- 관리자로 올리기: 올리는 관리자의 브라우저가 지금 있는 모든 묶음의 현재 세대 열쇠를 새 관리자 몫으로 건네는 자료를 함께 보낸다. 서버는 모든 묶음이 빠짐없을 때만 역할을 바꾼다(그 사이 묶음이 생기면 409로 다시 하게 한다).

### 5.2 초대와 가입

1. 관리자가 이름·아이디·역할을 넣으면 초대(72시간, 한 번만 사용)가 생긴다. 서버는 토큰 T의 HMAC만 저장한다. 메일은 보내지 않고 관리자가 링크를 메신저 등으로 직접 전한다. 취소할 수 있고, 다시 보내려면 새 초대를 만든다.
2. 초대받은 사람이 링크를 열면 브라우저가 T로 초대 정보를 받아 관리자 공개키를 S로 확인한다(4.4절).
3. 마스터 비밀번호를 정하면 브라우저가 열쇠를 모두 만들어 올린다. 아이디·이름·역할은 초대에 적힌 값만 쓰고 요청으로 바꿀 수 없다. 관리자로 초대한 사람도 계정은 우선 직원으로 만든다(짝 재확인 1). 복구 키를 보여 주고 "안전한 곳에 보관했어요"를 확인받는다.
4. 2단계 인증을 등록하면 `active`가 된다.
5. 초대한 관리자의 브라우저가 다음에 금고를 열 때 자동으로 공개키를 확인한다. 그 뒤라야 묶음에 넣을 수 있다. 화면에는 "확인 대기"로 보인다.
6. 관리자로 초대한 사람은 5번의 확인이 끝나는 즉시 초대한 관리자의 브라우저가 5.1절의 관리자로 올리기(모든 묶음 열쇠 건네기)를 함께 한다. 그 전까지는 직원이며 화면에 "관리자 지정 대기"로 보인다. 그래서 모든 관리자가 모든 묶음 열쇠를 가진다는 규칙이 깨지지 않는다.

### 5.3 묶음 권한

- 보기: 묶음의 항목 목록을 보고 비밀을 받아 보기·복사한다.
- 수정: 보기 + 항목 추가·수정·삭제.
- 같은 묶음 열쇠를 나눠 받으므로, 보기와 수정의 차이는 서버가 매 요청에서 검사해 지킨다.
- 묶음 만들기·이름 바꾸기·삭제, 구성원 추가·제외·권한 바꾸기는 관리자만 한다.
- 관리자는 구성원이 아니어도 모든 묶음을 수정 권한으로 연다. 화면에 "관리자 권한으로 보는 중"을 표시하고 열람 기록에 남긴다.

### 5.4 2단계 인증과 예비 코드

- TOTP(SHA-1, 6자리, 30초, 앞뒤 1구간 허용)를 `otpauth`(MIT)로 확인한다. 한 번 성공한 시간 구간과 그 이전 구간의 코드는 다시 받지 않는다.
- 서버가 비밀값을 만들어 `APP_SECRET_KEY`에서 나눈 열쇠로 암호화해 저장하고, 등록 화면은 브라우저에서 `qrcode`(MIT)로 QR을 그린다.
- 등록을 마치면 예비 코드 10개(각 Crockford base32 12자)를 한 번 보여 준다. 서버는 HMAC-SHA256만 저장하고, 쓰는 순간 한 번의 원자적 갱신으로 지운다. 다시 등록하면 옛 예비 코드는 모두 버린다.

### 5.5 로그인, 세션, 잠금

- 로그인: 아이디 → 소금과 변환 설정 받기(없는 아이디에도 `APP_SECRET_KEY`로 만든 같은 형태의 가짜 소금을 줘 존재를 숨김) → 로그인 확인값 → 2단계 인증 코드(또는 예비 코드) → 세션.
- 실패 문구는 아이디가 없든 비밀번호가 틀리든 같다("아이디 또는 비밀번호가 맞지 않아요").
- 세션 단계: 2단계 인증 대기(`pending_totp`, 5분), 2단계 인증 등록(`enroll_totp`, 15분), 복구 전 2단계 인증 등록(`recovery_enroll`, 15분), 복구(`recovery`, 10분), 정상(`full`, 8시간). 등록 확인을 마치면 `enroll_totp`는 `full`로, `recovery_enroll`은 `recovery`로 넘어간다. 정상 단계가 아니면 금고·라이선스·관리 API를 쓸 수 없다. 단계가 바뀔 때마다 세션 토큰을 새로 만들고 옛 토큰은 폐기한다.
- 서버는 만료를 직접 검사한다. 로그아웃, 비활성화, 복구, 비밀번호 바꾸기, 2단계 인증 초기화 때 그 사람의 다른 세션을 모두 폐기한다.
- 금고 잠금: 열쇠는 메모리에만 둔다. 15분 동안 조작이 없거나, 잠금 버튼을 누르거나, 새로 고침하면 잠긴다. 잠글 때 열쇠뿐 아니라 풀어 둔 목록·검색 결과·화면 상태도 지우고, 같은 브라우저의 다른 탭도 `BroadcastChannel`로 함께 잠근다. 타이머가 늦게 울려도 마지막 조작 시각을 다시 확인한다. 다시 열 때는 정상 세션 안에서 마스터 비밀번호만 넣는다.

### 5.6 분실과 재설정(짝 검토 5)

| 잃은 것 | 하는 일 |
|---|---|
| 마스터 비밀번호 | `/recover`에서 아이디 + 복구 키 + 인증 코드 → `recovery` 단계 → 새 마스터 비밀번호와 새 복구 키. 로그인 확인값·변환 설정·계정 열쇠 사본·복구 사본을 한 트랜잭션으로 바꾸고 모든 세션을 폐기한다. |
| 휴대폰(인증 앱) | 예비 코드로 로그인하면 `enroll_totp` 단계가 되어 새로 등록해야 정상 세션이 된다. 예비 코드도 없으면 관리자가 초기화한다. |
| 마스터 비밀번호와 휴대폰 | 예비 코드가 있으면 아이디 + 복구 키 + 예비 코드 → 옛 2단계 인증을 지우고 `recovery_enroll` → 새 인증 앱 등록 → `recovery` → 새 마스터 비밀번호. 예비 코드도 없으면 관리자가 2단계 인증을 초기화한 뒤 아이디 + 복구 키 → `recovery_enroll` → 같은 순서. 마지막 관리자도 예비 코드가 있으면 다른 사람 없이 혼자 복구한다(짝 재확인 2). |
| 마지막 관리자의 휴대폰과 예비 코드 | 다른 관리자가 없으므로 서버 운영자가 서버 콘솔에서 `npm run totp:reset -- <아이디>`로 2단계 인증을 초기화한다. 서버 운영자가 할 수 있는 일이라 금고 열쇠와는 관계없다. |
| 마스터 비밀번호와 복구 키 | 개인 금고는 영구 손실. 다른 관리자가 계정을 비활성화하고 새로 초대한 뒤 묶음을 다시 건넨다. |
| 마지막 관리자의 마스터 비밀번호와 복구 키 | 1단계에서는 되살릴 방법이 없다. 그 관리자의 개인 금고는 영구 손실이고, 다른 관리자가 없으니 초대·묶음·권한 관리도 더 할 수 없다. 직원들은 이미 받은 묶음 열쇠로 자기 묶음을 계속 쓴다. 직원에게 몰래 관리자 권한을 주는 우회로는 만들지 않는다. 이 경우를 막으려고 관리자 2명 이상을 계속 안내한다(5.1절). |

- 관리자의 2단계 인증 초기화·비활성화·역할 바꾸기·초대 만들기는 그 순간 관리자 본인의 인증 코드를 다시 받는다. 직원 본인 확인(전화·대면)은 화면에서 안내한다.
- 2단계 인증 초기화는 로그인 수단만 다시 만들게 하는 것이고 금고 열쇠와는 관계없다. 관리자가 직원의 개인 금고를 여는 사본은 어떤 경우에도 만들지 않는다.

### 5.7 퇴사·권한 회수

- 비활성화: 세션을 모두 폐기하고, 그 사람의 묶음 열쇠 사본을 모두 지우고, 그 사람이 열 수 있던 묶음마다 4.5절의 열쇠 교체를 한다. 관리자 브라우저가 교체 자료를 만들어 한 요청으로 보낸다.
- 구성원에서 빼기, 관리자를 직원으로 바꾸기도 같다.
- 그 사람이 열 수 있던 항목에 "비밀번호 교체 권장"을 표시한다. 항목을 고칠 때 "비밀번호를 새로 바꿨어요"를 고르면 표시를 지운다.

## 6. 항목 종류와 칸

| 종류 | 요약(목록·검색용) | 비밀 |
|---|---|---|
| 원격 접속 `remote` | 이름*, 업체, 접속 방식(RDP·AnyDesk·TeamViewer·SSH·VNC·기타), 주소(IP·호스트·원격 ID), 포트, 아이디 | 비밀번호, 메모 |
| DB 접속 `database` | 이름*, 업체, DB 종류(SQL Server·PostgreSQL·MySQL/MariaDB·Oracle·기타), 주소, 포트, DB 이름, 아이디 | 비밀번호, 메모 |
| 웹사이트 계정 `website` | 이름*, 업체, 주소(URL), 아이디 | 비밀번호, 메모 |
| 메모 `note` | 이름*, 업체 | 내용 |

- `*`는 필수. 각 글자 칸은 500자, 메모는 10,000자까지. 브라우저는 암호화하기 전에 JSON의 UTF-8 크기도 확인한다(요약 16,384바이트, 비밀 32,768바이트 이하). 한글 메모 10,000자(30,000바이트)와 비밀번호 500자가 함께 들어가도 이 안에 든다(짝 재확인 3).
- 검색은 브라우저에서 푼 요약(이름·업체·주소·아이디·DB 이름)을 대상으로 한다.
- 칸마다 복사 버튼을 둔다. 비밀번호 보기·복사는 서버에서 비밀 덩어리를 받아 온다. 복사한 값은 30초 뒤 클립보드를 읽어 그 값 그대로일 때만 지운다. 읽을 수 없거나(권한·포커스) 다른 내용으로 바뀌었으면 덮어쓰지 않고, "클립보드를 자동으로 지우지 못했어요"를 알린다(짝 재확인 4). 클립보드 기록 프로그램에 남은 사본은 지울 수 없다고 안내한다. 자동 지움이 늘 된다고 말하지 않는다.
- 웹사이트 주소는 `http:`·`https:`일 때만 "열기" 링크로 만든다.
- 항목 만들기·고치기 화면에 비밀번호 만들기 버튼(20자, 영문 대소문자·숫자·기호)을 둔다.
- 복호화한 글자는 React 글자로만 그리고 HTML로 해석하지 않는다.

## 8. API

모든 요청은 같은 출처의 `/api`로 보낸다(개발 서버는 Vite proxy가 백엔드 5000으로 넘긴다). 상태를 바꾸는 모든 요청(로그인·복구·초대 수락 포함)은 `X-KM-Request: 1` 머리글이 있어야 하고, `Origin`이 있으면 허용 출처와 같아야 한다. 비밀 값(토큰·확인값·복구값)은 주소가 아니라 본문으로만 보낸다.

| 묶음 | 요청 | 설명 |
|---|---|---|
| 상태 | `GET /auth/status` | `{ setupRequired }` |
| 설정 | `POST /auth/setup` | 설정 코드 + 첫 관리자 열쇠 자료 → `enroll_totp` 세션 |
| 로그인 | `POST /auth/prelogin` | `{ loginId }` → 소금·변환 설정 |
| | `POST /auth/login` | `{ loginId, authValue }` → `pending_totp` 또는 `enroll_totp` 세션 |
| | `POST /auth/login/totp` | `{ code }` 또는 `{ backupCode }` → 정상 세션 또는 `enroll_totp` |
| | `POST /auth/logout`, `GET /auth/me` | 내 정보·잠긴 열쇠·확인 기록 |
| 2단계 인증 | `POST /auth/totp/enroll/start`, `POST /auth/totp/enroll/confirm` | QR용 주소 / 코드 확인 → 예비 코드, `full` 또는 `recovery` 세션 |
| 계정 | `POST /auth/password` | 현재 확인값 + 새 소금·설정·확인값·계정 열쇠 사본 |

| | `GET /auth/recover/material` | `recovery` 세션에서 복구 사본·변환 설정을 받는다 |
| | `POST /auth/recover/complete` | 새 비밀번호 자료와 새 복구 자료 |
| 확인 기록 | `GET /trust`, `PUT /trust/:userId` | 내 계정 열쇠로 잠근 확인 기록(안전 번호 확인 등) 조회·저장 |
| 초대 | `GET /invites`, `POST /invites`, `POST /invites/:id/revoke` | 관리자 |
| | `POST /invites/lookup`, `POST /invites/accept` | 초대받은 사람(로그인 없음, 토큰은 본문) |
| | `GET /invites/pending-verification` | 관리자: 내가 만든 초대 중 수락했지만 아직 확인하지 않은 것(초대 비밀 사본·두 MAC·새 사람 공개키) |
| | `POST /invites/:id/verify` | 초대한 관리자: 내 확인 기록 + (관리자 초대면) 관리자 승인 서명과 모든 묶음 열쇠 사본 → `verified_at` |

## 9. DB 표

새 마이그레이션 하나로 아래 표를 만든다. 기존 `license_keys`는 고치지 않는다(평문 라이선스 키는 이번 범위 밖이며, 고객사 비밀을 그 표에 넣지 않는다).

- `users`: `id uuid PK`, `login_id varchar(64) UNIQUE`(소문자), `name varchar(100)`, `role`, `status`, `kdf_salt`, `kdf_params jsonb`, `auth_hash`, `auth_salt`, `recovery_auth_hash`, `recovery_auth_salt`, `account_key_master`, `account_key_recovery`, `enc_public_key`, `enc_private_key`, `sign_public_key`, `sign_private_key`, `totp_secret_enc NULL`, `totp_last_step bigint NULL`, `backup_codes jsonb`, `failed_attempts int`, `locked_until NULL`, `last_login_at NULL`, `invited_by NULL`, `admin_grant_sig NULL`(관리자면 필수), `admin_granted_by NULL`, `created_at`, `updated_at`
- `invites`: `id uuid PK`, `token_hash UNIQUE`, `login_id`, `name`, `role`, `created_by FK users`, `secret_enc`, `inviter_mac`, `expires_at`, `used_at NULL`, `accepted_user_id NULL`, `accept_mac NULL`, `verified_at NULL`, `revoked_at NULL`, `created_at`
- `trust_records`: `(owner_user_id, subject_user_id) PK`, `record_enc`, `updated_at`
- `sessions`: `id uuid PK`, `token_hash UNIQUE`, `user_id FK`, `stage`, `expires_at`, `revoked_at NULL`, `ip`, `user_agent`, `created_at`
- `vault_groups`: `id uuid PK`, `generation int`, `name_enc`, `created_by`, `created_at`, `updated_at`
- `vault_group_access`: `(group_id, user_id) PK`, `permission`(`view`·`edit`), `is_member bool`, `generation int`, `wrapped_key`, `shared_by FK users`, `share_signature`, `created_at`, `updated_at`. 묶음 삭제 시 함께 지운다.
- `vault_items`: `id uuid PK`, `group_id NULL FK`, `owner_user_id NULL FK`, 둘 중 하나만 있다는 CHECK, `key_generation int NULL`, `item_key_enc`, `summary_enc`, `secret_enc`, `revision int`, `needs_rotation bool`, `created_by`, `updated_by`, `created_at`, `updated_at`
- `audit_events`: `id bigserial PK`, `at`, `actor_user_id NULL`, `action varchar(40)`, `result varchar(16)`, `target_type`, `target_id`, `group_id NULL`, `detail jsonb`(비밀·제목·주소 없음), `ip`, `user_agent`

상한은 저장되는 `v1` 문자열의 글자 수로 정하고 브라우저·DTO·시험이 같은 값을 쓴다(짝 재확인 3). 요약 24,000자(평문 16,384바이트까지), 비밀 48,000자(평문 32,768바이트까지), 32바이트 열쇠 사본 200자, 암호화 개인키 4,000자, 서명 개인키 1,000자, RSA 사본 516자, 서명 90자, 확인 기록 6,000자. 개인키처럼 큰 사본은 따로 크기 시험을 한다.

## 10. 열람 기록(짝 검토 7)

- 필수 기록의 뜻은 "누가 언제 어떤 항목·개정의 비밀 덩어리를 서버에서 제공받았는가"다(`secret_delivered`, 목적 `view`·`copy`·`edit`). 사람이 실제로 봤는지·복사가 성공했는지는 증명하지 않는다. 한 번 받은 암호문을 브라우저가 다시 쓰면 기록이 남지 않는다.
- `secret_delivered`의 `detail`에는 목적(`purpose`)과 실제로 내준 행의 개정(`revision`)을 반드시 넣는다(짝 재확인 권장 2).
- 요약 목록을 내려받을 때도 `vault_synced`를 남긴다. 요약에도 주소·아이디가 있기 때문이다.
- 비밀 덩어리는 `POST /vault/items/:id/secret`으로만 나간다. 다른 API·동기화·편집 응답에 비밀을 넣지 않는다. 기록 저장이 실패하면 비밀을 내주지 않는다.
- 그 밖의 사건: 로그인 성공·실패·잠김, 2단계 인증 등록·초기화·예비 코드 사용, 비밀번호 바꾸기, 복구, 초대 만들기·취소·수락·확인, 역할 바꾸기, 비활성화·활성화, 묶음 만들기·이름 바꾸기·삭제·열쇠 교체, 구성원 추가·제외·권한 바꾸기, 항목 만들기·고치기·삭제. 관리자가 구성원이 아닌 묶음의 비밀을 받으면 `detail.asAdmin=true`.
- 비밀번호·제목·주소는 남기지 않고 ID·주체·행동·결과·시각·IP만 남긴다. 1단계에서는 지우지 않고 관리자만 본다. 서버 운영자가 기록을 지우거나 꾸미는 것은 막지 못한다(3절).
- 열람 기록 화면은 관리자가 가진 묶음 열쇠로 묶음·항목 이름을 풀어 보여 준다. 개인 항목은 "개인 항목"으로만 보인다.

## 11. 서버 보안 설정(짝 검토 8)

- `APP_SECRET_KEY`(base64 32바이트) 하나를 `.env`에 두고, HKDF로 2단계 인증 비밀값 암호화·예비 코드 HMAC·가짜 소금·토큰 HMAC 열쇠를 나눈다. `npm run secrets:init`이 값이 없을 때만 무작위로 만들어 `.env`에 넣고 화면에 찍지 않는다. 이 열쇠는 DB 백업과 따로 보관한다. 분실하면 2단계 인증 비밀값을 열 수 없고 예비 코드·세션·초대 토큰의 HMAC도 맞지 않으므로, 모든 세션과 초대가 무효가 되고 모든 사람의 2단계 인증을 초기화해야 한다. 관리자도 로그인할 수 없으므로 서버 운영자가 새 열쇠를 만든 뒤 `npm run totp:reset -- --all`로 초기화하고, 각자 다음 로그인 때 다시 등록한다(짝 재확인 3). 금고 열쇠는 이 열쇠와 관계없어 금고 내용은 잃지 않는다.
- 세션 쿠키: `__Host-km_session`(httpOnly, Secure, SameSite=Strict, Path=/, Domain 없음). `COOKIE_SECURE=false`(시험용)일 때만 `km_session`으로 Secure 없이 둔다. DB에는 토큰의 HMAC만 둔다.
- CSRF: SameSite=Strict + 상태를 바꾸는 모든 요청의 `X-KM-Request: 1` 확인 + `Origin` 확인. GET은 상태를 바꾸지 않는다. CORS는 허용 출처만, 자격 증명은 허용하지 않는다(같은 출처로만 쓴다).
- 시도 제한: 계정마다 로그인·2단계 인증·예비 코드·복구가 5번 연속 틀리면 15분 잠근다. IP마다 인증 경로(설정·로그인·복구·초대 조회·수락)는 1분 20번(`@nestjs/throttler`). 서버 PBKDF2는 동시에 4개까지만 돌린다.
- 요청 본문 상한: 4MiB(열쇠 교체 요청 때문). 칸마다의 길이는 DTO가 따로 제한한다. 열쇠 교체 요청 하나는 묶음 50개·사람 100명·항목 5,000개까지 받고, 넘으면 1단계 지원 규모를 넘었다고 413으로 거절한다. 비활성화·구성원 빼기는 필요한 모든 묶음의 교체가 같은 요청 안에서 끝나야만 성공한다. 남은 사람 중 아직 확인하지 않은 공개키가 있으면 끝난 것으로 표시하지 않는다(짝 재확인 권장 3).
- 화면 보안 머리글: 빌드한 `index.html`에 CSP(`default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'`)와 `referrer` `no-referrer`를 meta로 넣는다. 운영 서버는 같은 CSP에 `frame-ancestors 'none'`을 더해 응답 머리글로 보낸다(배포 때). 금고 화면에 외부 스크립트·분석 도구를 넣지 않는다. 개발 서버(HMR)에는 CSP를 넣지 않는다.
- 서버 로그와 오류 응답에 확인값·토큰·암호문·초대 링크를 남기지 않는다.

## 12. 오류 처리

- 풀기 실패(위조·열쇠 불일치): 그 항목만 "이 항목을 열 수 없어요"로 표시하고 나머지는 계속 보여 준다.
- 확인되지 않은 공개키·서명: 묶음 열쇠를 건네거나 쓰지 않고 안전 번호 확인을 안내한다.
- 세션 만료(401): 열쇠와 풀어 둔 내용을 지우고 로그인 화면으로 보낸다.
- 권한 없음(403): 금고를 다시 불러온다. 구성원에서 빠진 경우 그 묶음이 목록에서 사라진다.
- 동시 수정·세대 불일치(409): "다른 사람이 먼저 고쳤어요. 새 내용을 불러온 뒤 다시 하세요."
- 시도 제한(429)·계정 잠김: 언제 다시 할 수 있는지 알린다.
- 네트워크 오류: 입력한 내용은 지우지 않고 다시 시도 버튼을 보인다.
- 모든 오류 문구는 한국어로, 무엇을 하면 되는지 함께 쓴다.

## 13. 시험과 검증

- 프론트 암호 모듈(Vitest, Node 환경): Argon2id 알려진 답(RFC 9106 시험 벡터), 설정 범위 밖 거부, 묶음·항목 암호화 왕복, 한 바이트 위조·다른 AAD·다른 세대·다른 개정·다른 열쇠에서 실패, IV 중복 없음, 복구 키 형식·검사값, 서명·확인 기록·초대 HMAC, 안전 번호가 양쪽에서 같음, 열쇠 교체 후 옛 묶음 열쇠·옛 항목 열쇠로 새 항목을 못 품, 계정 만들기 → 잠금 해제 → 비밀번호 바꾸기 → 복구 흐름.
- 백엔드 단위 시험: 환경 검증, 확인값 해시·비교, TOTP 확인·재사용 거부, 예비 코드 일회 사용, 가짜 소금, 권한 판정.
- 백엔드 e2e(시험 DB `keymanager_test`): 설정 코드·한 번만 설정, 초대 → 수락 → 2단계 인증 → 로그인, 단계 세션으로 금고 API 거부, 묶음 → 구성원 → 항목 → 비밀 제공 기록, 비구성원 403, 보기 권한의 수정 403, 빼기·비활성화 때 세대·사본·항목 열쇠가 빠짐없어야만 성공, 비활성화 뒤 세션 폐기, 시도 제한·잠김, 머리글 없는 요청·다른 Origin 거부, 라이선스 API 로그인 필요, 비밀이 다른 응답에 섞이지 않음.
- 브라우저(Playwright): 관리자·직원 두 사람으로 전체 흐름(초대 링크 자동 확인 포함), 잠금·잠금 해제·다른 탭 잠금, 복사 후 클립보드, 빌드본(`vite preview`)에서 CSP 아래 Argon2 작업자 동작, `frontend-quality` 검증 기준(키보드, 대비, 1440·768·390 폭, 다크, 낮은 창, 움직임 줄이기, 한국어).
- DB 확인: 시험 자료의 비밀번호·이름·IP 글자가 DB 어느 칸에도 평문으로 없는지 읽기 전용 조회로 확인한다.
- 짝(Codex) 교차 검토: 고친 설계서, 암호 모듈, 인증·권한 API, 화면을 단계마다 따로 본다.

## 14. 구현 순서

각 단계는 시험을 먼저 쓰고(TDD), 검사(타입·린트·시험·빌드·취약점)를 종료 코드로 확인한 뒤 커밋한다.

1. 백엔드 기반: `APP_SECRET_KEY`와 `secrets:init`, 서버 쪽 비밀 도구(확인값 해시, TOTP, 예비 코드, 가짜 소금, 토큰 HMAC), 쿠키, 세션·CSRF·Origin 가드, 시도 제한, 열람 기록 서비스, 엔티티와 마이그레이션.
2. 백엔드 계정: 설정·로그인·2단계 인증·로그아웃·내 정보·비밀번호 바꾸기·복구·초대·확인 기록, 서버 콘솔 2단계 인증 초기화 명령(`totp:reset`). 마이그레이션을 시험 DB에 적용하기 전에 사용자 승인을 받는다.
3. 백엔드 금고: 묶음·구성원·열쇠 교체·항목·비밀 제공, 사용자 관리, 열람 기록 조회, 라이선스 API 가드.
4. 프론트 암호 모듈(`src/lib/crypto`)과 Argon2 작업자.
5. 프론트 기반: `/api` proxy, API 클라이언트, 라우터, 세션·금고 상태(자동 잠금, 탭 간 잠금), 앱 틀(메뉴), 빌드 CSP.
6. 인증 화면: 처음 설정, 로그인, 초대 수락, 복구, 금고 열기, 내 계정.
7. 금고 화면과 관리자 화면(사용자·확인·묶음·열람 기록).
8. 라이선스 화면을 새 디자인으로 옮기고 `components/legacy`와 Radix·sonner 의존성을 지운다.
9. 전체 검증과 짝 교차 검토, tm 갱신, 완료 보고.
